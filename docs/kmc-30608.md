# KMC 30608 Smart Tap: conversion and metering

Status on 2026-10-11: ESPHome installed; physical outlet, button and controlled
mains-cycle acceptance passed. The three existing HA entity IDs now use ESPHome.
All four native metering fields are enabled. A single-point voltage correction
has been applied to all three samples. The third sample additionally has an
approximate Emporia-based power/energy correction; current on all samples and
power/energy on the first two remain uncalibrated. The later sample sections
retain their separate acceptance limits.

## Observed device

The owner reports model KMC 30608, marked Type 3 SPD. Home Assistant's entity
registry and the saved LocalTuya configuration associate all three switches
with one device. Their relay datapoints are 1, 2 and 3 respectively. All three
were available and OFF during inspection. Exact entity mapping, credentials and
network identifiers remain in the private inspection record.

LocalTuya uses protocol version 3.1. That value does not identify the installed
vendor firmware version or prove compatibility with an OTA conversion exploit.
The initial inspection did not reset the device, operate its relays, change its
configuration or transfer firmware.

## Published hardware support

The [manufacturer's Smart Tap page](https://kmc.co/products/smart-tap) identifies
model 30608 and describes three independently controlled outlets plus one
always-on outlet. The [ESPHome device entry](https://devices.esphome.io/devices/kmc-smart-tap/)
links that product and documents an ESP8266 configuration with a 1 MiB board
target. It lists relay GPIOs 15, 13 and 14, button GPIO16, an inverted indicator
on GPIO1, and HLW8012 metering on GPIO12/4/5.

These assignments initially came from the published reference, not measurements
of this sample. The later conversion confirmed the chip, flash size, button and
the numbered relay-to-outlet order. Do not reuse the
different KMC 30137 single-relay profile.

## Conversion boundary

The model has an ESPHome reference profile.
[Tuya-Convert](https://github.com/ct-Open-Source/tuya-convert) depends on the stock
firmware accepting its handshake, and vendor patches can prevent this even on
ESP8266 hardware. The successful sample below does not establish compatibility
for every unit with the same model marking.

For a later conversion, use the existing unloaded-device workflow and a
GPIO-neutral first image. Verify each outlet before assigning its existing HA
role. Adapt the reference configuration to the selected ESPHome version, disable
UART logging before using GPIO1 for the indicator, and use the batch's
`ALWAYS_OFF` relay policy rather than copying the reference's restore behavior.
Metering and its calibration need separate validation. Preserve existing entity
IDs during the HA migration where possible, and inspect references to the old
device and integration before retiring its LocalTuya entry.

## Conversion observation

After the owner authorized conversion and confirmed all outlets unloaded, stock
firmware 1.0.5 accepted the ordinary Tuya-Convert procedure. The intermediate
VTRUST-FLASH 1.5 loader matched the original device identity and reported ESP8266,
normal boot, bootloader 4, and 1 MiB QIO flash at 40 MHz. A private full-flash read
was retained after the intermediate loader started; it is not a pristine factory
dump.

The 420,800-byte GPIO-neutral ESPHome 2026.9.1 image installed in 8,733 ms and
joined the home network with a verified encrypted API. An input-only probe
subsequently recorded an owner-confirmed GPIO16 press and release, active low.
The 429,312-byte relay image uses the reference GPIO15/13/14 assignments, an
inverted network-status indicator on GPIO1, and `ALWAYS_OFF` for all three relays.
The shared button switches all outputs off if any is on, or all on if all are off.

Native API checks independently exercised each reported relay state. A software
restart from all three ON returned all three OFF. These checks do not measure
voltage at the outlets or short boot transients. This initial relay image did not
enable metering; the subsequent update is described below.

The owner tested one lamp in each numbered outlet with only that channel ON.
The first and second lamps went dark when their channels were switched OFF and
the next channel was enabled. The third outlet's lamp switched OFF and ON with
the common button; native state events confirmed that all three relays followed.
After all outputs were ON, the owner removed mains power for five seconds and
restored it. The lamp remained dark and the encrypted API reported all three
outputs OFF with the same final build.

The [three-outlet hardware package](../examples/kmc-30608-three-outlet.yaml)
reproduces the tested relay/button behavior. The GPIO1 network-status indicator
follows the published reference; its visual behavior has not been independently
confirmed. The fourth, always-on outlet has no relay entity.

The native ESPHome device was added to HA, then this device alone was removed
from the shared LocalTuya entry. All three original entity IDs were transferred
to the matching ESPHome channels and ended available and OFF. The final source
and private credentials were saved in HA and the ESPHome Dashboard. No HA restart
or additional relay command was issued during the handover.

Subsequent HA service checks switched each channel ON and OFF independently.
All six state transitions matched their command contexts, the other two channels
stayed OFF, and the test ended with all outputs OFF. The shared LocalTuya entry
contains exactly one fewer device, with every other device configuration unchanged.
An existing notification automation still referenced an obsolete third-channel
entity alias in two places. Both references now use the preserved current ID;
HA configuration validation passed and automations were reloaded. Existing
dashboard and light-off script bindings continue to use their original IDs.

## Metering update

The owner requested all available measurements with calibration left for later.
The original application contains the `hlw8012.c` identifier. Together with the
published Smart Tap profile, this supported testing HLW8012 with SEL on GPIO12,
CF on GPIO4 and CF1 on GPIO5. The 432,560-byte ESPHome 2026.9.1 update retained
the verified relay/button configuration and added voltage (V), current (A),
active power (W) and energy since boot (kWh). HA discovered all four sensors on
the existing device, with the appropriate device and state classes; the three
switch entity IDs stayed unchanged. A diagnostic sensor reads `Not calibrated`.

The [optional metering package](../examples/kmc-30608-metering.yaml) reproduces
this configuration. It uses the component defaults of a 0.001-ohm current shunt
and voltage divider 2351, with a five-second update interval. Current and voltage
alternate on CF1, so they refresh less frequently than active power. The example
does not copy the reference device's voltage calibration.

With all relays OFF, a 35-second observation reported approximately 128.7 V,
0 W and 0.058–0.067 A. With the owner's test lamp on numbered outlet 3 only,
another 35-second observation reported about 128.1 V, 1.08–1.09 A and
138.6–140.7 W, while energy increased. These are uncalibrated firmware readings,
not reference measurements. The nonzero no-load current and small no-load energy
increment are retained as observations for later calibration; no arbitrary
offset or filter was applied to hide them. All relays were returned OFF.

This is one metering interface, not three independent per-outlet meters. Load
response was tested only on outlet 3; coverage of outlets 1, 2 and the always-on
outlet remains unverified. The
[native energy accumulator](https://esphome.io/components/sensor/hlw8012/)
starts from zero after a device restart. Its explicit `Energy Since Boot` name
and `total_increasing` state class preserve that distinction in HA. It is not a
persistent lifetime counter. Frequency, power factor and temperature are not
provided by this component.

Updated source and existing private credentials were saved in HA and the
ESPHome Dashboard. The public example was configuration-validated and compiled
for the 1 MiB target. Absolute accuracy still requires reference calibration.

### Voltage-only reference adjustment

When only a voltage reference is available, apply a per-device `multiply`
filter to the voltage sensor: reference voltage divided by the uncorrected
reading. Leave `voltage_divider` unchanged because the HLW8012 implementation
uses it for power and energy scaling too. Current, power and energy therefore
remain uncalibrated until independently compared with a suitable reference.
The [ESPHome calibration guide](https://esphome.io/components/sensor/hlw8012/#calibration)
describes the additional measurements needed for complete meter calibration.

Do not copy one sample's correction into the generic hardware package or every
other plug. Record each measured pair and distinguish a single reference point
from accuracy across the full voltage range. Comparing to a panel meter also
leaves branch voltage drop and phase assignment unverified.

An OTA update restarts these devices with all three relays OFF. When the plugs
are in service, arrange the brief power interruption and record the intended
relay states before updating one device at a time. The energy-since-boot sensor
also starts a new accumulation period; its history must not be rewritten.

On 2026-10-11, the owner supplied a 129.6 V reading against a calibrated Victron
reference of 122 V and requested correction of all three samples. An initial
adjustment to nominal 122 V left the three readings about 0.8 V below the live
reference. The factors were then refined using the median ratio of the mean
Victron L1/L2 voltage to each corrected KMC reading across five concurrent
snapshots. The final voltage-only multipliers are 0.948139981 for the first
sample, 0.955391577 for the second, and 0.933219142 for the third.

Phase assignment was not established, so using the phase mean is an approximate
single-point reference adjustment, not a claim of sub-volt accuracy at every
outlet or across the operating range. Branch voltage drop remains unmeasured.

All three 432,656-byte ESPHome 2026.9.1 images compiled and installed by native
OTA. Device identities, component keys, GPIOs, current/power/energy scaling and
the normal `ALWAYS_OFF` policy were preserved. The nine relay states were
recorded and restored after sequential updates. The diagnostic now explicitly
identifies voltage as referenced and the other measurements as uncalibrated.
All three sources passed validation in the Dashboard and were synchronized to
HA, the Dashboard and their private workbench sources. No universal calibration
factor was added to the public hardware example.

The final three-snapshot HA check reported medians of 122.74 V, 122.67 V and
122.72 V for the first, second and third samples respectively. The simultaneous
Victron readings were 122.38 V on L1 and 122.41 V on L2. The remaining difference
was about 0.3 V, within the limits of this approximate panel-reference check;
it was not treated as proof of outlet-level calibration accuracy. All nine
relay states still matched the recorded states after the updates.

### Third-sample approximate power/energy reference

Later on 2026-10-11, the owner reported that Living TV's shared power reading
exceeded the Emporia circuit containing Living, Dining and Bath2, and authorized
using Emporia as a provisional reference. The owner then confirmed the TV had
switched off and that other room devices normally consume about 120 W. This
allowed a comparison across the observed load change instead of treating the
entire circuit as the KMC's consumption.

During the ten-minute higher-load window, time-weighted means were 665.93 W
from KMC and 372.89 W from Emporia. A subsequent 125.67-second lower-load window
averaged 46.19 W and 160.16 W respectively. The correction is the change in
Emporia power divided by the change in KMC power: 0.343258. Splitting the higher
window into two five-minute windows produced factors 0.34654 and 0.33956.
The comparison implies about 144 W of background consumption outside the KMC;
this is an estimate, not a separately measured circuit load.

The deployed third-sample configuration applies `multiply: 0.343258` to power
and `multiply: 0.000343258` to energy, including its existing Wh-to-kWh conversion.
Voltage retains its earlier correction; current remains uncalibrated. The
diagnostic now reads `Voltage referenced; power/energy approx Emporia; current
uncalibrated`. The 432,736-byte image compiled and installed by native OTA;
the three recorded relay states were restored and verified. Matching sources
were saved and validated in HA and the ESPHome Dashboard and synchronized to
the private workbench configuration.

This remains a provisional calibration: it assumes the other circuit loads
were stable across the TV transition and inherits Emporia's accuracy and timing
limitations. A reference meter on the same load is needed to establish absolute
accuracy. The coefficient belongs only to this sample and must not be copied
to the other KMCs or the generic example. Existing HA energy history was not
rewritten; the device's energy-since-boot counter restarted with the update.

## Second sample: accepted relays, unresolved outlet indicators

A second owner-identified KMC 30608 also accepted ordinary Tuya-Convert from
stock firmware 1.0.5. The loader reported ESP8266 and 1 MiB QIO flash at 40 MHz.
A full flash read was retained privately after the intermediate loader started.
The GPIO-neutral image was 420,800 bytes, followed by an input-only probe that
recorded the common button on GPIO16, active low.

The 432,560-byte ESPHome 2026.9.1 relay/metering candidate passed independent
native control and software-restart checks. The owner used a fan to confirm
physical outlets 1, 2 and 3 match GPIO15, GPIO13 and GPIO14 respectively. An
initial unsuccessful lamp observation was superseded by the working fan test.
However, the owner reported that the separate indicators beside the outlets
remained dark. A temporary test image drove the known GPIO1 indicator output;
the owner confirmed that only the common indicator beside the button lit.
Inspection of the retained stock application's hardware table found its three
per-channel indicator fields set to the disabled mode. The initialization code
skips creating those indicator outputs. The table does configure the common
indicator on GPIO1. There is consequently no evidence for assigning additional
GPIOs to the separate outlet indicators. Their electrical behavior remains
unresolved; the standard firmware was restored after the diagnostic test.
The owner clarified that the individual indicators previously illuminated
with their loads. They therefore must not be classified as failed LEDs merely
because the reference profile omits them. After a cold mains cycle, the second
sample still powered the fan on outlet 3 while its indicator remained dark.
For comparison, the owner confirmed that the first sample's outlet 3 indicator
lit correctly. The two deployed GPIO/metering configurations differ only in a
source comment. This distinguishes the observed samples but does not identify
the electrical cause. The owner explicitly deferred further indicator diagnosis;
no additional GPIO experiments or hardware inspection were performed.

The stock table also exposes an important distinction: Tuya datapoint 1 uses
GPIO14, datapoint 2 uses GPIO13, and datapoint 3 uses GPIO15. On the physically
tested sample, these correspond to embossed outlets 3, 2 and 1 respectively.
Migration must preserve the old physical relay association, rather than assume
that a Tuya datapoint number equals the embossed outlet number. The first
sample's original table has the same ordering. After the owner confirmed it
was still on the work table without its usual loads, its HA roles for physical
outlets 1 and 3 were corrected to the stock datapoint association. Existing
entity IDs and role metadata were preserved, and no relay command was issued
during that registry correction.

The second sample passed its own common-button test with the fan on outlet 3.
After a five-second mains disconnection from all three ON, the fan remained
stopped and the same production build reported all three OFF. HA adoption and
source persistence passed; only this device was removed from LocalTuya, reducing
the shared entry from 35 to 34 devices with all other device configurations
unchanged. The three existing entity IDs were handed to the corresponding
physical relays. An obsolete alias in a notification automation was corrected
in two places; HA configuration validation and automation reload passed.

All four metering sensors are present. A no-load reading was about 128.0 V,
0.061 A and 0 W. The nonzero current is an uncalibrated offset observation,
not evidence of a connected load. Calibration was deferred at acceptance;
the later voltage-only adjustment is recorded above.

### Later role reassignment

After acceptance, the owner repurposed physical outlets 1 and 2 of the second
sample. The predecessor plugs were retained under neutral names before their
logical entity IDs were assigned to the KMC channels. Outlet 3 retained its
existing role. A registry check confirmed each final entity against the
ESPHome channel's unique ID and device ID; physical outlet numbers were not
inferred from old Tuya datapoint numbers.

The reassignment uses HA entity and device name overrides. The accepted
firmware and physical button behavior remain unchanged. No relay command or
additional flash was needed. Exact household roles and predecessor mappings
are recorded in the private deployment inventory.

## Third sample: stock 1.0.6 and DOUT flash

The third owner-identified KMC 30608 Type 3 SPD initially blinked only while its
button was held. After holding for about five seconds and releasing, the owner
confirmed sustained fast blinking. The first ordinary Tuya-Convert attempt
delivered the intermediate image but timed out waiting for the loader. With no
transfer active, the owner disconnected mains for five seconds. A second
attempt reached VTRUST-FLASH 1.5 on the isolated device.

The loader reported an ESP8266-family device with 1 MiB DOUT flash at 40 MHz,
unlike the previous samples' QIO. The 420,800-byte neutral image header was
checked against those parameters before transfer. A full post-loader flash
read was saved privately; it is not a pristine factory backup. Encrypted native
API identity and an input-only GPIO16 probe passed. One owner-confirmed press
produced an active-low press/release interval of approximately 0.177 seconds.

The retained stock 1.0.6 application contains the same 144-byte three-channel
initializer as the second sample: Tuya channel relay pins 14, 13 and 15, with
the common button on GPIO16. This supports the existing profile, but does not
replace per-unit physical load verification. The 432,560-byte ESPHome 2026.9.1
relay/metering image passed independent native channel controls and a software
restart from all ON to all OFF. The owner confirmed that physical outlet 1
powered the test load. The sequence was advanced to outlet 2 only, but before
confirming that load test the owner explicitly deferred further testing.
Physical outlets 2 and 3, common-button load control and mains-cycle acceptance
therefore remain unverified. Meter readings were uncalibrated at acceptance;
the later voltage-only adjustment is recorded above.

The third sample was not already configured in LocalTuya. HA adopted it as a
new ESPHome device with three switches, voltage, current, power, energy since
boot and a `Not calibrated` status. The four numeric sensors were available
with their expected units and state classes. A stalled configuration flow was
continued through the normal encryption-key step without restarting or
patching HA. Existing LocalTuya entity identities were preserved.

The complete source and unique credentials were persisted and read back in
both HA and ESPHome Dashboard, leaving prior secret values unchanged. No load
command was sent during adoption or source persistence. After the owner
deferred testing, cleanup returned all three outputs OFF and the encrypted
API confirmed the state on the expected device and firmware. No further test
cycles were run. HA service switching checks are also deferred, not passed.

## First sample repurposed for utility power

The owner later reassigned the first sample's three outlets from decorative
lighting to utility loads. Power-enable names describe the electrical supply,
not an instruction to operate an attached appliance. The original separate
controls were retained for a later physical handover. Exact household names
and channel identities are recorded in the private inventory.

The former lighting targets were removed from morning shutdown, shared
lighting/media shutdown and surplus-power decorative-light actions. Generic
state-change notifications follow the renamed channels. Lovelace groups the
new roles together. An active-reference scan found no remaining uses of the
three retired lighting entity IDs, and the new roles are not automatically
added to the Matter export filter. This change does not alter the firmware or
issue relay commands.

The first sample's dashboard was then consolidated into one device group:
three outlet controls and one shared set of voltage, current, power, energy
since boot and calibration-status readings. Obsolete per-appliance meter rows
were removed from the dashboard; their underlying entities and history were
retained. The actual water-valve control remains separate from its electrical
power supply. Renamed native sensor IDs preserve the existing hardware unique
IDs, units and state classes. The energy label still explicitly states that
the counter resets at device boot; no individual appliance histories were
summed into a fabricated total.

At the later handover, the former standalone plugs were renamed as spare
devices. Pump level-control rules and the related valve-recovery script now
follow the KMC's pump power-enable outlet. At the owner's explicit request,
both high-power protections use the KMC's shared power sensor, retaining the
700 W threshold and the existing three- and five-minute durations. These rules
remain enabled, but their input includes the other connected loads and is
still uncalibrated; it is not an individual measurement of pump consumption.
Active configuration checks and reference checks passed without test commands
to the pump or valve.
